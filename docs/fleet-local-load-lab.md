# Local fleet component load lab

This isolated component lab exercises fleet-shaped database and RPC load and
produces one source-attributed report. It is not chain E2E:

- `fleet-opportunity-planner` using the real planner and Yield migrations;
- signer-free revalidator and executor entrypoint probes;
- `fleet-route-confirmer`;
- the real route reconciler process;
- loopback PostgreSQL populated with deterministic synthetic queue history;
- a loopback Solana JSON-RPC emulator with latency, jitter, and deterministic
  error injection;
- concurrent worker-shaped SQL, user writes, mock chain observations, cached
  health reads, and a separately measured direct history-source control.

Health readers are rate-limited to one snapshot read per client per second.
Production workers emit health every ten seconds, so the lab retains a 10x
timing stress factor without turning health into an unbounded database flood.

Run the default 10,000-opportunity scenario:

```sh
bun run fleet:local-load-lab
```

Run a short smoke scenario:

```sh
bun run fleet:local-load-lab -- \
  --opportunities 1000 \
  --duration-seconds 5 \
  --output /tmp/fleet-local-load-lab-smoke
```

Exercise recovery with 80-120 ms RPC latency and every tenth request failing:

```sh
bun run fleet:local-load-lab -- \
  --opportunities 100000 \
  --duration-seconds 60 \
  --health-clients 3 \
  --rpc-latency-ms 80 \
  --rpc-jitter-ms 40 \
  --rpc-clients 32 \
  --rpc-error-every 10
```

After the first build, `--skip-build` reuses
`target/fleet-local-load-lab/debug/*`.

## Safety boundary

The entry script removes inherited database, RPC, observability-ingestion, and
signer variables. PostgreSQL binds only `127.0.0.1`, and the script refuses a
database name outside `fleet_e2e_*`. The RPC emulator binds only `127.0.0.1`.

Signer-requiring roles use their built-in signer-free role probes; this lab adds
no signer bypass to production code. Synthetic queues are moved out of the real
claim window. No `.env`, 1Password environment, account, or production data is
loaded.

## Evidence produced

Every run writes `artifacts/fleet-local-load-lab/<UTC timestamp>/` with:

- `evidence.md` and `evidence.json` for the correlated verdict;
- `planner-benchmark.json` for the real deterministic planner algorithm;
- per-role Rust logs and liveness-at-shutdown evidence;
- 500 ms CPU/RSS samples for every real worker process;
- separately attributed RPC method counts for real processes and the synthetic
  driver, plus latency, injected failures, and concurrency;
- PostgreSQL transaction, cache, tuple, temp-file, connection, wait, deadlock,
  relation-size, queue-state, and backlog snapshots;
- raw pgbench latency logs and per-role throughput;
- PostgreSQL server logs with lock-wait reporting enabled.

The report raises local thresholds for worker exits, deadlocks, health-query
p95 over 250 ms/1 s, RPC errors, and workload stderr. Machine-readable evidence
is retained so CI or a notebook can apply stricter capacity gates later.

## Recommended scenario matrix

Use the same host and build for each run, changing one dimension at a time:

| Scenario | Opportunities | Duration | RPC shape | What it isolates |
| --- | ---: | ---: | --- | --- |
| smoke | 1,000 | 5 s | 5 ms | wiring and safety gates |
| baseline | 10,000 | 60 s | 25 ± 10 ms | current local envelope |
| history | 100,000 and 1,000,000 | 60 s | 25 ± 10 ms | view/index growth |
| slow RPC | 100,000 | 120 s | 100 ± 100 ms | pool and lease pressure |
| brownout | 100,000 | 120 s | 80 ± 40 ms, every 10th fails | retry amplification |
| health fan-out | 100,000 | 60 s | 25 ± 10 ms, 1/3/10 health clients | observability contention |

Compare p95 and throughput curves, not only a single maximum. Scaling is risky
when health latency grows roughly linearly with durable history, worker RSS or
connection usage grows with queue depth, retries increase RPC concurrency, or
backlog drain throughput falls below the expected arrival rate.

Run the stateful validator path with provider-shaped latency only after the
LiteSVM gate passes:

```sh
bun run fleet:local-chain-e2e -- \
  --fixture fixtures/<capture>/manifest.json \
  --rpc-load-seconds 5 \
  --rpc-load-clients 16 \
  --rpc-latency-ms 80 \
  --rpc-jitter-ms 40
```

`--rpc-error-every N` is also available for bounded fault experiments. A run
with production-process RPC errors is expected to fail the full-chain verifier
unless every affected role recovers and the verifier is deliberately extended
to prove that recovery. Do not reinterpret synthetic driver errors as worker
retry evidence.

## Interpretation boundary

High-cardinality pressure is generated by explicitly labelled synthetic SQL and
RPC clients while route payloads remain quiesced. The report does not count
liveness or synthetic activity as real-worker progress. It covers component
startup, polling, database contention, RPC fault injection, and resource use;
it does not cover Kamino decoding, validator execution, transaction landing,
Neon autoscaling, Render limits, or provider capacity. `FULL_CHAIN_E2E` remains
`NOT_RUN` until a stateful local-chain fixture proves every pipeline stage and
pre/post token balances.
